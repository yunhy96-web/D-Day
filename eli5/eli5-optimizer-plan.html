🚗 SQL은 목적지만 말해요

🗣️ "김씨인 주문
다 보여줘!"
(무엇을 = SQL)
➡️
🧭 "어떻게 갈지는
내가 정할게"
(어떻게 = 옵티마이저)

우리는 "무엇을"만 말해요.
"어떻게"(인덱스? 풀스캔? 어떤 조인?)는
내비게이션인 옵티마이저가 골라요

⚖️ 여러 길에 점수를 매겨요

🛣️고속도로
(풀 스캔)
비용 80
🏘️골목길
(인덱스 + NL 조인)
비용 12 ⭐
🌉다리 건너기
(해시 조인)
비용 35

후보 경로마다 비용(cost) 점수를 계산하고
제일 싼 길을 골라요.
이게 비용 기반 옵티마이저(CBO)

비용 = 블록을 몇 번 읽을까 + CPU + 메모리... 의 예상치예요

🗺️ 점수의 재료는 '지도 데이터'

📊 통계정보
행이 몇 개인지
값이 어떻게 퍼져 있는지
클러스터링 팩터는 몇인지

내비가 좋아도 지도가 낡으면 엉뚱한 길로 가요.
통계가 오래되면 옵티마이저도 이상한 계획을 세워요 😵

📌 "갑자기 쿼리가 느려졌어요!"의 단골 범인
= 데이터는 확 늘었는데 통계는 옛날 것

📋 실행계획 = 확정된 경로표

내비가 고른 길을 출발 전에 미리 볼 수 있어요

EXPLAIN SELECT ... ;

1. tb_order 테이블을
   ref — 인덱스(idx_name)로 콕 집어 접근
2. tb_product 테이블을
   eq_ref — PK로 한 건씩 매칭 (NL 조인)

"어느 테이블 먼저? 인덱스 탔나? 무슨 조인?"
이 전부 적혀 있는 계획서예요

MariaDB는 EXPLAIN, Oracle은 실행계획 트리를 안쪽(들여쓰기 깊은 곳)부터 읽어요

🚨 계획서에서 이런 게 보이면 빨간불

🐢 ALL (풀 스캔) — 큰 테이블인데 첫 장부터 다 읽는 중
📚 filesort / temporary — 줄 세우기·임시 공책을 따로 만드는 중
🔢 rows가 예상 밖으로 큼 — 생각보다 많이 읽을 예정

튜닝 = 계획서를 읽고 → 빨간불을 찾고 →
인덱스·SQL을 고쳐 더 싼 길을 열어주는 것

👉 힌트 = "이 길로 가!"

🧭 내비 추천대로
(기본: 옵티마이저 믿기)
☝️ "아니야, 골목길로 가"
USE INDEX(...), STRAIGHT_JOIN
= 힌트로 수동 지시

내비가 계속 이상한 길을 고르면
사람이 직접 길을 지정할 수 있어요.
단, 지도가 바뀌어도 고집하니 조심!

📝 정리하면

SQL = 무엇을 · 옵티마이저 = 어떻게
후보 경로마다 비용 계산 → 제일 싼 길 선택 (CBO)
점수의 재료는 통계정보 —
낡은 지도는 이상한 계획을 만든다
실행계획(EXPLAIN)은 출발 전 경로표 —
튜닝은 여기서 빨간불을 찾는 것부터
