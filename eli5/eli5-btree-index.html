1쪽... 2쪽... 3쪽...

이게 풀 스캔(Full Scan).
확실하지만... 너무 오래 걸려요 🐢

🏢 B-tree는 3층 건물이에요

🏢루트 — 1층 안내 데스크
"ㄱ~ㅁ은 왼쪽, ㅂ~ㅎ은 오른쪽"
⬇️ ⬇️
🪧브랜치 — 층 안내판
"ㄱ~ㄷ은 1번 방..."
🪧브랜치
"ㅂ~ㅅ은 3번 방..."
⬇️ ⬇️ ⬇️
🗄️리프
강감찬→3쪽
김철수→87쪽
🗄️리프
나영희→12쪽
박민수→55쪽
🗄️리프
이몽룡→9쪽
홍길동→31쪽

맨 아래 리프에는 이름이 가나다순으로,
옆에는 "본책 몇 쪽인지" 주소가 적혀 있어요

🔍 찾기는 딱 3걸음

1️⃣데스크에서
"ㄱ이니까 왼쪽!"
➡️
2️⃣안내판에서
"1번 방!"
➡️
3️⃣서랍에서
"김철수→87쪽!"
➡️
📖본책
87쪽 펴기

천만 명이어도 3~4걸음이면 도착!
데이터가 10배 늘어도 걸음은 딱 1개 늘까 말까 ✨

이게 로그(log) 시간의 힘 — 트리의 '높이'만큼만 걸어요

🔗 리프끼리는 손잡고 있어요

"김씨부터 박씨까지 전부!" 같은 범위 검색은
시작점만 찾고 → 옆으로 죽~ 걸어가면 끝이에요

📌 SQLP 포인트: 찾기 = 수직 탐색(루트→리프) 한 번
+ 수평 스캔(리프 옆으로) — 이 두 동작이 전부예요

⚖️ 공짜는 아니에요

✍️ 새 학생이 오면
안내판도 고쳐야 해요
(INSERT/UPDATE가 느려짐)
📚 안내판 자체도
자리를 차지해요
(저장 공간)

그래서 인덱스는 많이 만들수록 좋은 게 아니라
자주 찾는 것에만 골라 만들어요

🚫 안내판이 무용지물 되는 순간

🔧 이름을 가공해서 물어보기
SUBSTR(name,1,1) = '김' — 안내판은 원본 순서로만 정렬돼 있어요
🔚 끝 글자로 찾기
LIKE '%철수' — 가나다순 안내판은 첫 글자부터 봐야 해요
🙅 "김씨 아닌 사람 전부"
부정형(!=)은 결국 거의 다 봐야 해요

인덱스 컬럼은 가공하지 말고 그대로 비교!
(좌변 가공 금지 — SQLP 단골 문제 ⭐)

📝 정리하면

B-tree = 루트 → 브랜치 → 리프 3층 안내판,
리프에는 정렬된 값 + 본책 주소
찾기 = 수직 탐색 몇 걸음 + 리프 옆으로 스캔
→ 천만 건도 순식간
대신 쓰기가 느려지고 공간을 먹으니 골라서 만들고,
컬럼을 가공하면 못 쓴다
