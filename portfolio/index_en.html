D-Day — Korean–Thai bilingual community platform

Solo full-cycle · In production

A community shared by Korean and Thai speakers. When someone posts, AI translates it automatically so readers in the other language see it in their own, and a crawler collects content from external communities to seed the platform.
Stack: Spring Boot 3.2 · Java 17 · PostgreSQL · OpenAI API · Expo(React Native) · GitHub Actions · EC2

Backend design highlights

  • Async AI translation pipeline outside the transaction boundary — @TransactionalEventListener(AFTER_COMMIT) plus @Async separate post persistence from translation. An external API (OpenAI) failure never rolls back the domain transaction, and PENDING→PROCESSING→COMPLETED/FAILED state transitions keep failures traceable
  • Dynamic scheduler framework without redeployment — job settings live in the DB and a REST API toggles them on/off and switches the interval (Cron ↔ fixedRate) at runtime. An interface registry pattern means adding a new job only requires registering one implementation
  • Restart-safe crawler — the crawl cursor (last page) is persisted in the DB so collection resumes after an interruption, a unique sourceId key makes it idempotent, and sleeps between requests handle rate limiting
  • DB-driven dynamic RBAC — the role × post-type permission matrix lives in a table rather than in code, and allowed types are pushed down as query conditions to filter at the DB level
  • Timezone-based localization — stored in UTC and converted to the user's timezone in responses; the client infers language from the timezone and falls back between the translation and the original (localization from server data, without an i18n library)
  • Frontend token refresh concurrency control — the axios interceptor performs the refresh only once on a 401, queuing concurrently failing requests and retrying them together with the new token
  • CI/CD — GitHub Actions → Docker Hub → automated EC2 deployment; the frontend serves an Expo web build through a multi-stage Nginx image

FlashArena — Concurrency & distributed system failure simulator

Solo build · Technical proof

A dashboard that uses a first-come-first-served flash sale to prove visually, through live logs, that concurrent requests without a lock drive stock negative while a Redis distributed lock stops it exactly. I built it to demonstrate what I know through reproducible experiments instead of explaining it in words.
Stack: Java 21 · Spring Boot 3 · Redis · PostgreSQL · SSE · Vite + React + TypeScript

  • Race condition reproduction — No-Lock mode actually produces oversold and negative stock, and Redis distributed lock mode proves under identical conditions that exactly the available stock is decremented
  • Transactional Outbox + Redis Streams — the order transaction and event publication are recorded atomically, then a relayer publishes asynchronously, and the payment consumer uses UNIQUE-constraint idempotency so duplicate events still charge only once
  • MSA constraint simulation — isolates auth/order/payment schemas within a single DB and forbids cross-schema FKs, JOINs, and shared transactions to reproduce the constraints of a distributed environment (UUID for all PKs)
  • SSE live log streaming — streams processing steps per run (runId) to the frontend dashboard in real time

PackFit — 3D box-packing simulator

Solo build · Algorithm implementation

Enter box and item dimensions, and a 3D bin-packing algorithm computes the layout, replayed step by step in Three.js. Built with pure TypeScript and browser rendering only — no framework, no backend.
Stack: TypeScript · Three.js · Vite · Vitest

  • Hand-implemented EP-BFD (Extreme-Point + Best-Fit-Decreasing) — 6-way rotation, 70% floor-support check, fragile (nothing stacked on top) and max-weight constraints; tries 4 sort strategies and keeps the layout with the most items packed and highest fill rate
  • A pure function that knows nothing about spacing — the box shrinks by wall clearance and items inflate by their gap, so pack() stays a deterministic, DOM-free function that is easy to test
  • Invariant-based tests — a shared assertion ("inside the bounds, no two items overlap") applied to every case (Vitest), plus recommending the smallest Korea Post standard box (No. 1–6) that fits everything
  • Visualization UX — step-by-step packing replay slider, hover tooltips, localStorage input restore
