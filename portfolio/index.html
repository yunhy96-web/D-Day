CASE 01

외부 벤더 발권·취소 신뢰성 계층

앳홈트립 · 2026.06 – 08 · 설계·구현 단독
사고. 재발권 후 두 번째 취소가 주문 단위 멱등키에 중복으로 걸려 벤더에 전달되지 않았다. 고객 환불은 나갔고 벤더 좌석은 그대로 남았다. 발권·취소는 돈이 걸린 양자 작업인데 동기 호출 한 번으로 끝내고 있었고, 타임아웃 뒤 단순 재시도는 중복 발권을 만들었다.

설계 — Outbox 상태 전이

처리 경로 3개: 1분 주기 폴러 · afterCommit 비동기 · 동기 인라인(SYNC_BLOCKING). 10분 넘게 PROCESSING에 방치된 건은 자동 회수. 모든 발권·취소 이력은 append-only 감사 테이블에 보존.

결정 세 가지

락 대신 조건부 UPDATE로 처리권 선점릴레이가 여러 인스턴스에서 돌아도 한 건은 한 번만 잡힌다.
락을 잡고 외부 호출을 기다리면 락 유지 시간이 곧 벤더 응답 시간이 된다.
타임아웃은 재시도하지 않는다SUCCESS/FAILED와 별도로 PENDING_VERIFY를 두고 운영자 확인으로 넘긴다.
타임아웃은 벤더 쪽에서 성공했을 수 있다. 재시도하면 중복 발권이다.
환불 직전 취소는 동기로, 실패하면 환불 차단상태 전이는 별도 트랜잭션으로 분리해 환불이 롤백돼도 실패 사유는 남긴다.
비동기로 보내면 환불이 나간 뒤에야 취소 실패를 알게 된다. 이게 사고의 원형이었다.
Ventrata·Galaxy Connect·Trip.com·Ingresso·Broadway Inbound 5개 벤더에 동일 계층 적용. 취소 실패 → 환불 차단으로 자금 불일치 원천 차단, DEAD 알림은 정확히 1회. 취소 전략 전용 테스트 작성.
기여도 100%
CASE 02

외부 티켓 벤더 5사 연동

앳홈트립 · 2025.12 – 2026.08 · 외부연동 모듈 69/100 커밋
사고 둘. 60초 넘는 벤더 호출 동안 DB 트랜잭션이 열려 있어 선등록한 주문 옵션이 미커밋 상태로 남았고, 후속 UPDATE가 0건 처리되거나 락 대기 타임아웃이 났다. 또 짧은 간격의 재시도가 벤더 호출 한도를 넘겨 정상 요청까지 연쇄 거부됐다.

설계 — 트랜잭션 밖 비동기 확정

결제 직전 재검증은 2026-08-10 캘린더–벤더 재고 불일치를 실측한 뒤 도입. 미결제 유령 주문이 확정에 채택되지 않도록 차단.

FlashArena

동시성·장애 시뮬레이터

"락 없이 동시 요청을 보내면 재고가 음수로 깨지고, Redis 분산 락을 걸면 정확히 막힌다"를 실시간 로그로 증명하는 대시보드.

  • Race condition 재현 — No-Lock 모드에서 재고 오버셀을 실제로 만들고, 분산 락 모드에서 정확히 재고만큼만 차감됨을 같은 조건으로 비교
  • Transactional Outbox + Kafka — 주문 TX와 outbox INSERT를 원자적으로, 릴레이어가 orderId 파티션 키·acks=all로 발행. 결제 Consumer는 수동 오프셋 커밋 + UNIQUE 제약 멱등 처리로 중복 이벤트에도 결제 1회
  • MSA 제약 시뮬레이션 — auth/order/payment 스키마 격리, 스키마 간 FK·JOIN·공통 TX 금지, SSE로 runId별 로그 스트리밍
주문 ─▶ [TX] 재고 차감(락 모드별) + Outbox INSERT ─▶ Relayer ─▶ Kafka(3 partitions, key=orderId) ─▶ 결제 Consumer(UNIQUE 멱등 → 오프셋 커밋) ─▶ SSE 로그

ThaiUnionTour

이벤트 기반 예약 커머스 · M2 완료

요구사항·도메인 모델·ERD·API 명세·인프라 설계 문서 8종을 먼저 쓰고 마일스톤 단위로 구현한 예약 커머스. Java 17 · Gradle 멀티모듈(DDD) · PostgreSQL · Redis Streams · Flyway · Next.js 14.

  • 선착순 동시성 — UPDATE … WHERE stock ≥ qty 원자 차감과 예약 INSERT를 한 트랜잭션으로 묶어 오버부킹 차단
  • 결제 파이프라인 — 입금 승인 시 확정 + Outbox를 한 TX로, Relayer는 FOR UPDATE SKIP LOCKED로 경합 없이 발행, Consumer는 UNIQUE 멱등 후 XACK
  • 경계 설계 — catalog/reservation/payment/member 스키마 분리, 교차 FK 없이 UUID 논리 참조. Flyway 소유권은 api 모듈 하나로
